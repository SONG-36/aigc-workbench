## 1. 文档职责

定义商品营销图片制作过程中，运营意图的来源、作用范围、继承关系、修改边界及历史版本保护原则。

**核心目标：避免 AI 在多张图片生成及多轮修改中，逐渐偏离运营已经提供或确定的商品信息、营销卖点、参考设计和修改要求。**

本文档属于业务契约，不规定 Prompt、Context Manager、Agent、模型记忆、调用次数或工程实现。

## 2. 三模式的意图来源

### Quick-A

`OPERATOR_CONFIRMED`

- 实际商品图决定最终商品外观。
- 同款同配置营销参考提供初始营销内容、适用卖点及设计方向。
- 运营可以通过整体、逐图和修改要求调整制作内容。
- 不要求额外填写 Listing。

### Quick-B

`OPERATOR_CONFIRMED`

- 实际商品图决定最终主体、配置及配件。
- 运营选定参考图，默认认为参考营销内容适用于目标商品。
- 参考提供初始营销与视觉方向。
- 必须完整替换参考商品主体及相关细节。
- 默认先生成，运营随后局部修改。

### Listing

`OPERATOR_CONFIRMED`

- 运营商品资料是商品信息与营销内容的主要依据。
- 实际商品图提供可见外观依据。
- 参考图主要用于视觉设计。
- 只有真正影响制作的关键问题才需运营确认，其余直接生成候选。

### 原始资料与 AI 结果

`PROPOSED`

运营资料、运营明确要求、AI 建议、生成候选、修改结果和人工 Pass 具有不同的业务含义。

AI 生成过某项内容，不代表运营确认其为商品事实。

## 3. 运营意图的四个层级

### 商品级

`OPERATOR_CONFIRMED / PROPOSED`

包括商品身份、真实外观、结构、配件和有依据的商品信息。

适用于同一目标商品的相关图片。

不同图位可以展示不同卖点，但不得无依据改变商品事实。

### 图包级

`OPERATOR_CONFIRMED / PROPOSED`

包括整体运营要求、明确指定的共同风格、语言、地区及其他整组限制。

Quick-A/B 的参考图通常来自同一商品链接，已有风格一般相对一致。

不默认额外生成统一风格方案，也不强制所有图片采用相同构图。

### 单图级

`OPERATOR_CONFIRMED / PROPOSED`

包括图位、绑定参考、尺寸、逐图要求、本图采用的营销内容和设计重点。

单图的参考及要求不得无依据影响其他图位。

本图未展示某项适用卖点，不等于该卖点不适用。

### 修改级

`OPERATOR_CONFIRMED`

针对运营当前选定的图片版本提出具体修改。

每次修改应区分：

- 修改基础版本。
- 当前仍有效的业务要求。
- 本轮修改目标。
- 应保持的已有内容。
- 新候选图片。
- 当前有效交付版本。

## 4. 信息来源与权限

`OPERATOR_CONFIRMED`

| 来源 | 使用原则 |
|---|---|
| 实际商品素材 | 最终商品外观依据 |
| Quick-A 参考 | 同款适用营销信息及设计依据 |
| Quick-B 参考 | 运营默认认为适用的营销内容与设计依据 |
| Listing 商品资料 | 商品信息和营销内容主要依据 |
| Listing 设计参考 | 主要提供视觉设计 |
| 整体要求 | 在明确作用范围内生效 |
| 逐图要求 | 作用于对应图位 |
| 修改反馈 | 作用于指定图片版本和修改范围 |
| AI 自行生成的内容 | 不自动成为商品事实或已批准要求 |

信息权限不能简单按时间先后决定。

新的制作要求不能无依据覆盖实际商品事实。

## 5. 运营要求的继承与变化

### 5.1 默认制作

`OPERATOR_CONFIRMED`

没有额外文字要求时：

- Quick-A 按同款营销参考的内容及设计方向制作。
- Quick-B 按运营默认认可适用的参考信息制作，并替换商品主体。
- Listing 按运营商品资料制作，以参考辅助设计。

不要求额外编写完整营销方案，也不强制完整方案人工预审。

### 5.2 新增整体及逐图要求

`PROPOSED`

新要求在其明确指定的范围内生效。

与重要商品事实产生冲突时，不能简单采用“最后输入优先”。

应按冲突实际影响范围处理。

### 5.3 整体要求变化后的已 Pass 图片

`OPERATOR_CONFIRMED`

1. 新整体要求默认作用于之后制作的图片。
2. 已 Pass 图片保持不变。
3. 不自动重新生成或使其失效。
4. 运营明确要求重改已 Pass 图片时，才开展新制作。
5. 新修改产生独立候选，不静默覆盖原 Pass。

### 5.4 历史制作依据

`PROPOSED`

图片版本应能追溯其制作时实际使用的商品资料、参考、整体要求、逐图要求及修改反馈。

后续要求变化，不应重写历史图片当时的制作依据。

### 5.5 要求冲突

`OPERATOR_CONFIRMED / PROPOSED`

- 保留发生冲突的信息来源与范围。
- 不自行创造商品事实解决矛盾。
- 能限定到单图或单项内容的，不默认阻断整组。
- 必须由运营决定的重要问题，进行针对性确认。
- 非关键未知不要求运营全部补齐。

### 整体要求与单图要求的实质冲突

`OPERATOR_CONFIRMED`

当运营主动重新修改已经 Pass 的图片时，如果新的整体要求与该图片仍有效的原单图要求存在明确、无法同时满足且实际影响本次制作的冲突，系统只针对该冲突向运营提出确认。

没有实质冲突时，不增加人工确认步骤。其他不受影响的图片和内容保持原样，不重新启动无关制作任务。

## 6. 图包意图保持

### 6.1 参考图组

`OPERATOR_CONFIRMED`

参考图由运营人工选择，通常来自同一商品链接。

系统以已有营销和设计方向为起点，不默认增加独立全局风格设计步骤。

### 6.2 图位独立

`PROPOSED`

单图生成、修改和审核不自动改变其他图位的参考绑定、要求或结果。

### 6.3 共同要求与例外

`PROPOSED`

整体要求按实际覆盖范围生效。

存在明确单图例外时，可按例外处理，但不得违反商品真实性约束。

### 6.4 已 Pass 图片

`OPERATOR_CONFIRMED`

已 Pass 图片不因新的整体要求自动重做或失效。

除非运营明确提出，不自动将某张已 Pass 图片作为其他图位唯一的设计标准。

## 7. 多轮修改的业务规则

### 7.1 修改目标

`PROPOSED`

运营可以针对当前选中的候选图片或历史版本提出修改。

本轮修改应聚焦运营希望改变的内容，不意味着重新规划全部商品、卖点和设计。

### 7.2 修改基础版本

`OPERATOR_CONFIRMED — V0.3`

**默认使用运营当前明确选中的图片版本作为修改基础。**

- 选择 V3，则以 V3 修改。
- 主动选择历史 V1，则可以从 V1 创建新候选。
- 不强制使用最新生成版本。
- 实际修改来源应与运营选中版本一致。
- 新候选不得静默覆盖基础图片或历史 Pass。

### 7.3 修改范围保持

`PROPOSED`

本轮未要求改变的内容应尽可能保持：

- 实际商品身份、外观与配件。
- 未要求改变的已采用营销内容。
- 已认可的文字和视觉设计。
- 其他图位及其已 Pass 图片。

若从较早历史版本修改，不应假定该基础图片拥有后来其他版本中的修改结果。

### 7.4 历史修改意见的继承

`OPERATOR_CONFIRMED — V0.5`

**采用：选定基础版本 + 当前有效要求 + 本轮修改。**

具体业务规则：

1. 本次修改以运营明确选中的图片版本为起点。
2. 当前仍有效的商品信息、整体要求、逐图要求及禁止事项继续约束制作。
3. 本轮修改反馈明确当前需要改变的内容。
4. 已经体现在基础图片中、且本轮未要求改变的设计和内容应尽可能保持。
5. 不要求重新执行从首次生成至今的全部历史修改指令。
6. 已被后续要求明确取代的历史要求，不再作为并列有效指令重新执行。
7. 历史修改要求及其结果仍需保留，供查询、对比和追溯。
8. 若当前要求与商品事实或其他仍有效的重要约束冲突，应针对具体问题处理。

**示例**

- V1：首次生成。
- V2：背景改为浅灰。
- V3：标题放大，浅灰背景保持。
- V4：运营选中 V3，要求主体向右移动。

V4 的业务期望：

- 使用 V3 作为基础图片。
- 保持浅灰背景及已调整标题。
- 执行主体右移。
- 遵守实际商品事实和当前有效要求。
- 不重新执行 V1～V3 的全部历史修改文字。

**历史记录用于追溯，不等于历史中的每条修改指令永远有效。**

### 7.5 当前有效要求与基础图片

`PROPOSED`

基础图片可能包含先前生成模型的错误，因此：

- 选择某张基础图片，不等于确认其全部商品内容真实。
- 仍有效的商品事实和业务约束不因图片中存在错误而失效。
- 如果发现重要矛盾，应以真实商品及已确认信息为依据处理。

这项原则不要求每次修改都重新进行完整商品资料审核。

### 7.6 修改与商品事实

`OPERATOR_CONFIRMED / PROPOSED`

修改不得无依据新增商品功能、参数、配件或认证。

重要矛盾应针对本次内容处理，不默认重新审核整组任务。

### 7.7 修改结果评价

`PROPOSED`

应检查：

1. 本轮目标修改是否实现。
2. 未要求改变的重要内容是否保持。
3. 是否引入新的商品事实或营销错误。
4. 运营是否认可新的候选结果。

生成成功不等于修改成功。

## 8. Pass 与交付版本

### 8.1 Pass 的含义

`OPERATOR_CONFIRMED`

Pass 表示运营认可某张图片的具体版本。

不等于 AI 调用成功，也不表示整组图片全部完成。

### 8.2 已 Pass 版本保护

`OPERATOR_CONFIRMED`

- 已 Pass 图片不因新的整体要求自动失效。
- 新生成或修改不静默覆盖原 Pass。
- 原图片和审核历史保持可追溯。
- 历史 Pass 版本继续可查看。

### 8.3 新候选与原 Pass

`OPERATOR_CONFIRMED — V0.4`

**新候选未 Pass 时：**

- 原 Pass 仍为当前有效交付版本。
- 新候选不能自动替代它。
- 新候选失败或被拒绝，不影响原有效版本。

**新候选被运营 Pass 后：**

- 新 Pass 自动成为该图位当前有效交付版本。
- 原 Pass 继续保留为历史通过版本。
- 当前交付及导出采用新的有效版本。

这里的替代只由运营 Pass 触发，不因模型生成成功自动发生。

### 8.4 修改来源与审核历史

`OPERATOR_CONFIRMED / PROPOSED`

- 每次修改应关联实际基础图片版本。
- 不得把从 V1 进行的修改记录成从 V3 开始。
- 修改及 Pass 记录不得被新候选覆盖。
- 当前有效交付版本与历史已通过版本应明确区分。

## 9. 关键疑点处理

`OPERATOR_CONFIRMED / PROPOSED`

- 非关键未知不默认阻断整组制作。
- 无依据的商品参数不得擅自补造。
- 可选卖点存在疑问时，可以限定受影响内容。
- 必保留内容存在重要冲突时，针对性提交运营确认。
- Quick-A/B 参考信息未独立认证，不自动等于不可采用。
- Listing 的主要营销内容依据运营提交的资料。

## 10. 运营意图验收

`PROPOSED`

| 维度 | 主要检查问题 |
|---|---|
| 商品保真 | 外观、结构、配件是否正确 |
| 营销意图 | 卖点及文字含义是否保持 |
| 参考设计 | 是否延续选定参考的合理方向 |
| 整体要求 | 是否遵守本次制作时适用的要求 |
| 单图要求 | 是否遵守当前图位要求 |
| 修改准确 | 本轮目标是否实现 |
| 非目标变化 | 是否改变不该改变的内容 |
| 修改来源 | 是否使用运营选定版本 |
| 历史继承 | 是否保留已实现内容，避免旧指令重新生效 |
| Pass 保护 | 新旧交付版本关系是否正确 |
| 可追溯性 | 是否保留制作依据、修改和审核历史 |

具体评价方法在 `03_ACCEPTANCE_CASES.md` 中定义。

## 11. 待确认事项

`TO_VERIFY`

1. 本轮修改反馈与原参考设计方向发生冲突时，哪些变化可直接执行，哪些需要确认？
2. 运营实际最常遇到的非目标变化是什么，哪些会使其重新开始制作整张图片？

### 已确认、不再重复询问

- 整体要求与单图要求的实质冲突按第 5.5 节已确认规则处理。
- 整体要求改变不自动修改已 Pass 图片。
- 修改默认以运营当前选中版本为基础。
- 可以从历史版本创建新候选。
- 新候选未 Pass 时不替代当前交付。
- 新候选 Pass 后成为当前交付，原 Pass 保留历史。
- 多轮修改采用基础版本、当前有效要求和本轮反馈；不重新执行全部历史修改指令。
